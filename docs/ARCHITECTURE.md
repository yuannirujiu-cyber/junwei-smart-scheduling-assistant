# 架构说明 · 君威智能排产助手

> 面向：接手这个仓库的开发者、要把引擎搬到别处复用的工程师、要评估落地可行性的技术评委。
> 读完本文你应该能回答三件事：**系统怎么分层、数据怎么流动、要换成自己的工厂该改哪里。**

---

## 一、定位与范围

一句话：**把订单排到具体机台与时间、解释每条安排的依据、支持人工调整并评估影响的多工序排产工作台。**

| 维度 | 现状 |
|---|---|
| 形态 | 浏览器端单页应用 + 零依赖静态服务器；**没有后端进程**，全部计算在浏览器内完成 |
| 依赖 | 运行时零第三方依赖、零 CDN；开发期只需要 Node 与（可选的）Python + openpyxl 跑数据校验 |
| 规模基线 | 323 张订单 / 906 条工序任务 / 109 台设备，首排约 80 ms，全流程约 170 ms |
| 持久化 | 浏览器 IndexedDB（数据快照 / 方案版本 / 审计日志 / 会话指针），可恢复、可清空 |
| 明确不做 | ERP/MES 双向集成、现场报工、库存采购、财务罚款结算、多工厂优化、移动端 |

**为什么把计算放在浏览器里？** 赛题要求「可运行的作品」，现场演示不能依赖网络与服务器环境；
同时排产是**单计划员、单次批处理**的场景（现状：每天排一次、每次 2–4 小时），
在浏览器里跑 906 条任务的启发式求解只需不到 0.1 秒，没有必要引入服务端复杂度。
需要服务端时的迁移路径见 §6.4。

## 二、分层

`~
┌──────────────────────────────────────────────────────────────┐
│ 视图层  web/src/views/*  +  components/*                      │
│   D00 设置 · D01 数据准备 · D02 订单中心 · D03 工作台（甘特）    │
│   D04 工序抽屉 · D05 版本与导出 · D06 异常重排 · D07 负荷分析     │
├──────────────────────────────────────────────────────────────┤
│ 状态层  web/src/core/store.js（单一数据源 + 发布订阅）           │
│   数据快照 · 求解状态 · 方案版本 · 人工干预 · 模拟 · 审计         │
├──────────────────────────────────────────────────────────────┤
│ 引擎层  web/src/engine/*（与界面完全解耦，可在 Node 中独立运行）  │
│   spec 规格解析 → capacity 设备与产能 → mapping 工艺映射          │
│   → model 建模 → scheduler 求解 → validate 校验 → metrics 指标    │
│   → explain 解释；rules 是 R1–R10 规则登记表                     │
├──────────────────────────────────────────────────────────────┤
│ 数据层  data/*.json（数据快照）· web/src/data/*（Excel/CSV 解析） │
├──────────────────────────────────────────────────────────────┤
│ 基础设施  core/dom（模板层）· core/util · core/persist（IndexedDB）│
│          core/diagnostics（错误边界 / 日志 / 诊断包）· export/*（导出）│
└──────────────────────────────────────────────────────────────┘
`~

**依赖方向单向向下**：视图依赖状态，状态依赖引擎与基础设施，引擎只依赖同层模块与 `core/util`。
引擎**不 import 任何 DOM 或 store**，因此可以在 Node、CLI、甚至服务端里直接跑。

## 三、数据流

### 3.1 起点是空白（没有隐式数据源）

应用启动时 `store.resetToBlank()` 把快照置为 `blankSnapshot()`：订单 0 条、设备 0 台、版本 0 个，
并停在 D01。**没有任何代码路径会在启动时自动 fetch 数据快照**；`?data=real|demo` 只作为显式深链存在。

数据只有四个显式入口，四条路径最终都汇集到同一个 `store.loadDataset()`：

| 入口 | 说明 |
|---|---|
| 订单文件（.xlsx / .csv） | 浏览器内解析 → 字段映射人工确认 → `buildSnapshotFromSheet` |
| 设备 / 产能文件（.xlsx） | `data/deviceImport.js` → `store.applyDeviceData`（无快照时以 `blankSnapshot()` 为底座） |
| .json 数据快照 | 校验 `orders` / `machines` / `capacity` 三个字段后直接载入 |
| 内置快照按钮 / `?data=` | 演示与自检用途，界面持续标注来源 |

就绪度由 `store.intakeStatus()` 从快照本身推导（订单数 / 设备数），不额外维护一份状态：
两部分齐备才 `settleIntake()` → 自动建立快照并首排；只到位一半则明确写出还缺哪一份，**不排产**。
在已经完整的会话里替换单份文件时不会自动重排，由用户决定何时重算。

## 四、三套状态机（不要混为一谈）

| 对象 | 状态链 | 关键约束 |
|---|---|---|
| **数据快照** | 未导入 → 处理中 → 待修复 / 可用 | 替换导入生成新快照；旧版本标记「基于旧数据」，历史输入不被覆写 |
| **求解任务** | 待开始 → 计算中 → 有可行解 / 无完整可行解 / 已取消 / 失败 | 取消保留原计划；无解时保留诊断信息，不伪造成功 |
| **方案版本** | 草稿 → 待重算 → 可确认 → 已确认 → 已替代 | 已确认版本**不可原地编辑**，改动会自动派生草稿 |

订单的**执行状态**（未开工 / 进行中 / 已完工）与**排产状态**（未排 / 部分排 / 已排）分开表达；
没有可靠在制数据时执行状态显示「未知」，不因为计划开始时间已过就推断正在生产。

## 五、关键设计决策

| 决策 | 理由 |
|---|---|
| **引擎与界面完全解耦** | 排产逻辑是资产，界面是壳。解耦后引擎可在 CLI / 服务端 / 测试里直接跑，也便于替换前端 |
| **零第三方依赖** | 现场演示不能因为网络或版本问题挂掉；同时免去供应链审查（制造业客户很在意） |
| **数据快照不可变 + 版本内容指纹** | 「确认」是审计动作，必须能回答「这份计划是基于哪份数据、内容有没有被改过」 |
| **演示参数显式标注** | 换型耗时矩阵与工艺映射数据包未提供。宁可在界面与导出文件上持续标注「模拟结果，含未验证参数」，也不假装数据齐全 |
| **约束可解释由结构化数据驱动** | 解释卡片的每条证据都来自求解过程记录（候选机台数、评估位置数、换型触发字段），不引入语言模型自由发挥 |
| **人工干预用完整锁定语义** | 不引入含义模糊的「部分锁」；锁定 = 锁定机台 + 起止时间，重算保持不变 |
| **R6（工序间隔 ≤72h）不放松** | 超出即阻断确认，靠「排除订单 + 重算」的显式路径收敛，而不是静默放宽约束 |
| **持久化失败不影响主流程** | IndexedDB 不可用 / 配额不足时降级为内存态并在界面如实告知，不阻塞排产 |

## 六、扩展点

### 6.1 接自己的数据
准备一份符合 `docs/DATA_CONTRACT.md` 的 JSON（或按 D01 的字段映射导入 Excel），
最少需要：订单（标识 / 规格 / 数量 / 交期）、设备台账、各工序的设备—规格产能矩阵。
矩阵空值一律按「不适配」处理——这是硬约束，不会被平均值或 0 填充。

### 6.2 换一条工艺链（不只是三道工序）
工艺链定义（工序数、名称、设备编号前缀、适配方式）支持注入，默认是拉丝 / 捻股 / 合绳。
把工序数改成两道或四道时，建模、排产、校验、指标都会跟着走，见 `docs/ENGINE_API.md`。

### 6.3 加一种导出格式
导出统一走 `web/src/export/exporters.js` + `web/src/export/xlsxWriter.js`（自研零依赖 xlsx 写入器）。
新增格式时请在文件头补上「版本 / 数据快照 / 导出范围 / 确认状态 / 模拟参数标识」——
这是 PRD 的硬要求，也是审计留档的最低条件。

### 6.4 加后端
引擎层可以直接搬到 Node：`web/src/engine/*` 不依赖 DOM。
建议路径：加一个 `POST /schedule` 接口（入参：数据快照 + 设置；出参：版本对象），
前端把 `store.generate` 换成一次请求即可，其余状态机与界面无需改动。
多人协作时把 `core/persist.js` 换成服务端存储，并复用已有的乐观锁（`rev`）与冲突提示。

## 八、已知边界（如实披露，不隐藏）

1. **换型耗时、成品→股型工艺映射、各工序需求量系数**在数据包中缺失，当前用显式标注的演示参数补齐；
   启用后版本标记为「模拟参数」，导出文件持续标注，不进入正式已确认状态。
2. **合绳完成 ≠ 实际发货**。界面用「预计合绳完工」与预发货日对比，是赛题范围内的**交付预测代理指标**。
3. **未接 ERP/MES**，确认动作只表示本产品内的人工认可，界面不显示「已下发生产」。
4. **R6 存在能力边界**：真实数据首排后仍有若干处工序间隔超 72 小时的订单，
   系统阻断确认并提供一键收敛（排除 → 重算），不静默放宽；被排除的订单在确认页与导出首页显式列出。
5. **会话持久化是浏览器本地的**，换浏览器或清空站点数据即丢失；生产部署应把持久化换到服务端（见 §6.4）。
6. 未实现完整制造流程（热处理 / 编结 / 检测 / 包装）、拆单并行、多工厂优化。
