## 一分钟读懂这张图

```
订单进入 → ① 校验(R7) → ② 工艺映射与建模(R1) → ③ 前瞻派单核心 → ④ 后处理与校验 → ⑤ 版本确认导出
```

其中第 ③ 步是本算法的重点，也是「最优」这个词被准确定义的地方：

**每次机台空闲时**
1. 筛出候选订单：本工序已就绪 · 机台兼容 · 未被占用（三条缺一不可）；
2. 算两个余量：`S`（交期余量）与 `G`（工序间隔余量，对应 R6 的 72 小时）；
3. 分层：紧急可行 → 负余量 → 普通可行；层内按 `min(S, G)` 最小者优先；
4. 取 `d` = 层内最紧急订单，`c` = 层内「本机同型号且完全可行」的最紧急订单；
5. 按四行规则决策：
   - `d` 同型号，或没有可行的 `c` → **加工 d**；
   - `d` 有更早的可行下一台 → **本机加工 c（不换型）+ 把 d 预约到下一台**；
   - `d` 在本机可行（等待会违约或超 72h）→ **立即换型加工 d**；
   - 都不行 → **让位给同层其他可行订单 + 登记风险**，绝不静默放宽。

## 关于「最优」的准确表述

**这不是数学意义上的全局最优解**。设计文档 §12 自己写明它是「可实现、可解释的启发式初版」。
准确说法是：**在给定目标序（硬约束 → 交期 → 延期时长 → 利用率/换型）下，用「单步前瞻 + 设备预约」
求出的局部最优派单**，不做回溯、不做多步搜索。它保证什么、不保证什么，见算法说明第 0 节。

## 重新生成

图与文字都由脚本生成，改文案不会破坏版式：

```bash
cd 君威智能排产助手
node tools/build_flowchart.mjs     # 重新生成 01-*.svg 与 排产决策流程图.html
node tools/check_flowchart.mjs     # 校验图与说明文档（含与引擎常量的一致性）
```

> 流程图不是手绘的：30 多个节点与 40 多条连线的坐标由 `tools/build_flowchart.mjs` 的
> 极小布局层（band / box / diamond / arrow）算出来，改文字不会让连线错位。
